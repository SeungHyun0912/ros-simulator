# ROS 2 · Isaac Sim 기반 Adapter 검증 환경 아키텍처

- 문서 버전: 0.1 — 구현 전 설계안
- 작성 기준일: 2026-09-21 (KST)
- 대상 규모: AMR 10대 / 협동로봇 5대 / PLC 연계 설비는 단계적 추가
- 검증 대상: 별도 개발하는 장비별 Adapter Middleware
- 이번 개발 범위: ROS 2 가상 장비 제어기, Isaac Sim 연동, 시나리오·장애 주입·결과 판정
- 제외 범위: 통합 관리 시스템 및 Adapter 자체 구현

> **핵심 요약**
>
> 1. Adapter 아래에 실제 장비의 인터페이스를 제공하는 ROS 2 가상 제어기를 둔다.
> 2. 가상 제어기는 명령·상태·오류를 관리하고, Isaac Sim은 동작·물리 상태·시각화를 담당한다.
> 3. 초기에는 지정 경로 이동과 사전 정의된 관절 동작으로 시작하며, Nav2·MoveIt 2는 선택 사항으로 둔다.
> 4. 같은 장비 인터페이스 뒤에서 Isaac Sim 실행 모드와 경량 실행 모드를 교체한다.
> 5. 1대+1대 기능 검증 후 10대+5대로 확장하고, 성능 시험은 시뮬레이터 부하와 분리한다.

## 문서 해석 기준

- **공식 기능 설명**에는 참고 자료 번호 `[Sxx]`를 붙였다.
- **제안·초기값·패키지명·노드명·인터페이스명·일정**은 본 프로젝트를 위한 설계안이다. 제품의 내장 기능이나 성능 보장이 아니다.

- 본 문서는 동작·통신 검증 설계이며, 실제 장비의 안전 인증이나 실제 로봇 제어 성능을 보증하지 않는다.

# 1. 전체 Architecture 구성

## 1.1 목표와 검증 경계

### 이번 환경으로 검증할 것

- Adapter의 명령·응답·상태·오류 매핑
- 목표 접수와 실제 완료의 구분
- 취소, 실행 실패, 시간 초과, 재요청 처리
- 다중 장비 동시 접속과 장비별 상태 격리
- 장비 제어기 재시작 및 상태 재동기화
- AMR·협동로봇·설비 사이의 인계 조건
- 메시지 부하에 따른 지연·처리량·자원 사용량

### 초기에는 검증하지 않을 것

- 실제 벤더의 주행·모션 제어 알고리즘 정확도
- 실제 센서 노이즈, 위치 추정 오차의 정밀 재현
- 실제 그리퍼의 파지력 및 접촉 안정성
- 실제 PLC 스캔 주기와 필드버스 타이밍
- 실제 안전 PLC, 비상정지 회로, 안전 정격 기능

**중요:** 자체 정의한 ROS 2 인터페이스로 합격했다고 특정 벤더 장비와의 호환성이 입증되지는 않는다. 벤더 연동을 주장하려면 그 장비의 메시지 정의·동작 의미·오류·QoS 계약을 재현해야 한다.

## 1.2 논리 구성도

코드나 추가 렌더러 없이 읽을 수 있는 구성도다.

**외부 개발 영역**

통합 관리 시스템 또는 Adapter 상위 인터페이스용 테스트 클라이언트  
↕ 상위 업무 명령·상태  
AMR Adapter / 협동로봇 Adapter / 설비 Adapter **[검증 대상]**

**검증 경계: 실제 배포에서 사용할 ROS 2 인터페이스**

↕ Topic · Service · Action

**이번 개발 영역 A — ROS 2 가상 장비 계층**

- AMR 가상 제어기 × 10
- 협동로봇 가상 제어기 × 5
- 설비 가상 제어기 × 필요한 수량
- 공통 작업 상태 머신 / 명령 원장 / 오류 모델
- 실행 Backend 선택

↙ **Isaac 실행 Backend**　　　　　　　　　↘ **경량 실행 Backend**

**이번 개발 영역 B — 실행 환경**

- Isaac: ROS 2 Bridge ↔ 가상 로봇·설비·센서·물리·화면
- 경량: 타이머·위치 보간·상태 모델로 결과 생성, GPU 불필요하도록 설계

**공통 테스트 지원 계층**

시나리오 실행기 / 장애 주입 / 독립 검증기 / 로그·지표 수집 / 실행·초기화 관리

### 테스트 명령 경로를 분리한다

- **통합 시험:** 테스트 클라이언트 → 실제 Adapter → 가상 제어기 → Backend.
- **시험 장치 자체 시험:** 테스트 클라이언트 → 가상 제어기 → Backend.
- 두 번째 경로의 성공을 Adapter 검증 성공으로 계산하지 않는다.
- 장애 주입과 초기화는 별도의 테스트 관리 인터페이스로 수행한다. 정상 업무 인터페이스에 섞지 않는다.

## 1.3 계층별 책임과 상태의 기준

| 계층 | 책임 | 담당하지 않는 것 |
|---|---|---|
| 외부 통합 관리 시스템 | 작업 할당, 공정 흐름, 필요 시 교통 정책 | 이번 문서의 구현 대상 아님 |
| 외부 Adapter | 업무·장비 인터페이스 변환, 장비 상태 처리 | 가상 장비 내부 구현 |
| 가상 제어기 | 명령 검증, 작업 수명주기, 상태·오류 응답 | 렌더링, 물리 계산 |
| 실행 Backend | 목표를 실행 수단으로 변환, 실행 결과 수집 | Adapter의 업무 정책 |
| Isaac Sim | 가상 위치·관절·충돌·동작 상태 생성 | 관제 작업의 성공 의미 결정 |
| 테스트 지원 계층 | 시나리오·장애·판정·기록 | 정상 장비 상태를 임의로 성공 처리 |

**상태의 기준을 명시한다.**

- Isaac 실행 모드의 실제 위치·관절 상태: Isaac Sim 관측값.
- 작업의 접수·실행·완료·실패 상태: 가상 제어기 상태 머신.
- 통신 이상 상황에서 Adapter가 받은 값: 장비가 보고한 상태.
- 테스트 기대 결과: 별도 작성한 인터페이스 계약과 시나리오.
- 물리 상태, 보고 상태, 기대 상태를 따로 기록해 오류 주입 시 차이를 추적한다.

## 1.4 실행 모드

| 모드 | 실행 방식 | 목적 | 한계 |
|---|---|---|---|
| 경량 모드 | 타이머·상태 머신·간단한 위치 모델 | Adapter 회귀·부하·장애 시험 | 충돌·파지 물리 검증 불가 |
| Isaac 모드 | Bridge와 로봇 제어 연결 | 동작·인계·공간 상태 정합성 | 물리·렌더링 부하가 지연에 영향 |
| 상세 제어 모드 | Isaac + Nav2 또는 모션 스택 | 실제 제어 스택 관련 상호작용 | 구성·튜닝 범위 증가 |

모드가 바뀌어도 Adapter에 노출하는 Action·Service·Topic과 작업 상태 의미는 유지한다. Nav2 사용 여부도 Adapter 외부 계약과 분리한다.

## 1.5 배포 구조

### 초기 구성: 단일 워크스테이션

- Isaac Sim: 별도 프로세스.
- ROS 2 가상 제어기: 초기에는 장비별 프로세스.
- 테스트 실행기·검증기·기록기: 별도 프로세스.
- Adapter: 별도 프로세스 또는 외부 호스트.
- 첫 연동은 네이티브 설치로 확인하고, 이후 필요한 영역만 컨테이너화한다.

장비별 프로세스를 제안하는 이유는 특정 장비 제어기의 종료·재시작을 다른 장비와 분리해 시험하기 위해서다. 메모리와 CPU 비용은 목표 규모에서 측정한다.

### 확장 구성: 시뮬레이션 호스트와 시험 호스트 분리

| 호스트 | 실행 대상 |
|---|---|
| GPU 호스트 | Isaac Sim, ROS 2 Bridge |
| CPU 호스트 | 가상 제어기, 시나리오, 수집·판정 |
| Adapter 시험 호스트 | 실제 Adapter와 상위 테스트 클라이언트 |

- 처음에는 같은 LAN과 같은 RMW 구현을 기준으로 한다.
- Discovery·방화벽·멀티캐스트·컨테이너 네트워크 구성을 먼저 점검한다.
- 테스트 환경마다 별도 ROS Domain을 할당한다.
- Domain 분리는 논리적 통신 구분이며, 보안 경계는 별도 네트워크 정책으로 만든다. Domain ID의 논리 네트워크 역할은 ROS 공식 문서를 참조한다. [S10]
- 초기에는 하나의 Isaac Sim 월드에 15대를 배치한다. 다중 프로세스·다중 GPU 분산 물리 월드 구성은 초기 범위에서 제외한다.

## 1.6 반드시 고정할 아키텍처 결정

1. Adapter에 노출하는 장비 인터페이스는 Backend와 독립적이다.
2. 사용자 정의 업무 Action은 외부 ROS 2 프로세스에서 처리한다.
3. Isaac Sim에는 가능한 한 표준 메시지만 전달한다.
4. Isaac 모드에서는 관측 피드백 없이 목표 전송만으로 성공 처리하지 않는다.
5. 실시간 시험과 가속·일시정지 가능한 기능 시험을 구분한다.
6. ROS 2 가상 제어기가 통합 관리 시스템의 작업 할당 로직을 대신 구현하지 않는다.
7. 가상 제어기에는 장비 자체의 사용 중 거부·정지·기본 인터록만 둔다. 전역 교통 정책은 책임 주체를 별도 결정한다.

# 2. ROS 2 내부 구성

## 2.1 개발 범위와 구성 원칙

ROS 2 계층은 **장비 인터페이스 에뮬레이터 + 실행 관리자**로 개발한다.

- Python 중심으로 시작한다.
- 장시간 이동·작업은 Action 형태의 외부 계약으로 설계한다.
- 짧은 조회·설정은 Service, 주기적 상태는 Topic으로 설계한다.
- 작업 실행 루프가 상태 발행·취소 처리를 막지 않게 구성한다.
- Isaac Sim 프로세스 안에 모든 ROS 2 업무 로직을 넣지 않는다.

ROS 2의 RMW 계층이 통신 추상화를 제공하며, 미들웨어와 QoS 선택이 연결 동작에 영향을 준다. 본 설계에서는 DDS 기반 Fast DDS를 초기 후보로 정하고 동일 설정으로 검증한다. [S01][S10]

## 2.2 패키지 구성안

아래 패키지명은 **직접 만들 프로젝트 패키지명**이며 기존 배포 패키지가 아니다.

| 제안 패키지 | 주요 내용 | 우선순위 |
|---|---|---|
| `virtual_device_interfaces` | 상태 메시지, 작업 Action, 조회·제어 Service | 필수 |
| `virtual_device_core` | 상태 머신, 명령 ID, 결과 원장, 오류·시간 정책 | 필수 |
| `virtual_amr` | AMR 업무 인터페이스, 이동 실행 관리 | 필수 |
| `virtual_manipulator` | 프로그램 실행, 관절 동작 관리 | 필수 |
| `virtual_equipment` | Conveyor·Lift·AS/RS의 상태·인터록 모델 | 후속 |
| `execution_backends` | Isaac 연결 및 경량 실행 구현 | 필수 |
| `test_bringup` | 장비 목록·설정 로딩, 실행 구성 | 필수 |
| `scenario_testkit` | 시나리오·장애 주입·독립 판정 | 필수 |
| `test_observability` | 이벤트 로그, 메트릭, 보고서 | 필수 |
| `robot_description_assets` | 필요 시 URDF·TF·시각화 설정 | 권장 |

인터페이스 정의 패키지와 구현 패키지를 분리한다. Adapter 개발팀에는 인터페이스 버전, QoS, 상태 전이, 오류 정의, 샘플 테스트를 함께 제공한다.

## 2.3 장비별 노드 구성안

### AMR 1대의 논리 구성

- `amr_device_node`
  - 명령 검증·Action 서버·작업 상태·상태 발행.
  - 일대일 장비 식별자와 명령 원장 관리.
- `amr_motion_backend`
  - 지정 경로 이동 또는 Nav2 호출.
  - 현재 위치와 도착 여부를 제공.
- `device_fault_profile`
  - 명령 거부·지연·동작 정지·상태 누락 정책.
  - 초기에는 별도 노드가 아닌 가상 제어기 내부 모듈로 구현.

### 협동로봇 1대의 논리 구성

- `manipulator_device_node`
  - 프로그램 시작·취소·상태·결과.
- `joint_sequence_backend`
  - 사전 정의된 관절 목표 순서 실행.
  - 관절 피드백과 허용 오차로 완료 판정.
- `cell_interlock`
  - 화물 존재·AMR 도착·셀 점유 조건.
  - 초기에는 작업 셀 내부 모듈로 구현.

### 공통 노드

- `scenario_runner`: 명령 발생과 시험 순서 제어.
- `fault_orchestrator`: 특정 장비·시간·조건에 장애 적용.
- `assertion_monitor`: 독립적인 합격·실패 판정.
- `event_collector`: 명령·상태 전이·장애·시간 기록.
- `environment_manager`: 준비 상태 확인, 실행 종료, 초기화.

**논리 모듈 수와 OS 프로세스 수는 동일할 필요가 없다.** 초기에는 장비 1대당 프로세스 하나에 업무 노드와 Backend 모듈을 배치하는 정도로 제한한다.

## 2.4 Namespace와 좌표계

### 이름 규칙 제안

| 종류 | 예시 |
|---|---|
| AMR | `/amr_01` ~ `/amr_10` |
| 협동로봇 | `/arm_01` ~ `/arm_05` |
| 설비 | `/conveyor_01`, `/lift_01`, `/asrs_01` |
| 테스트 제어 | `/test` |
| 시뮬레이션 데이터 | `/sim/amr_01`, `/sim/arm_01` |

### TF 설계 제안

- 공용 월드 기준: `world`.
- AMR별 프레임: `amr_01/odom`, `amr_01/base_link` 등.
- 협동로봇별 프레임: `arm_01/base_link`, `arm_01/tool0` 등.
- 공통 `/tf`, `/tf_static`을 사용하는 초기 구성을 제안한다.
- Namespace뿐 아니라 메시지 내부의 `frame_id`와 `child_frame_id`도 장비별로 설정한다.
- 각 TF 변환은 발행 주체를 하나로 정한다. Bridge와 외부 노드의 중복 발행을 금지한다.
- Nav2 추가 시 `map → odom → base_link` 관계와 월드 좌표 변환을 별도로 확정한다.

`tf2`, `tf2_ros`, 관련 메시지 패키지는 ROS 2 Jazzy 패키지 구성에 포함된다. 위 프레임 구조는 프로젝트 설계안이다. [S11]

## 2.5 Adapter에 제공할 장비 계약

실제 대상 시스템이 이미 인터페이스를 가지고 있다면 **아래 제안보다 실제 계약을 우선한다.**

| 장비 | 외부 이름 예시 | 방식 | 의미 |
|---|---|---|---|
| AMR | `/amr_01/move_to` | 사용자 정의 Action | 목적지 이동 |
| AMR | `/amr_01/state` | 사용자 정의 Topic | 운전·작업·위치·오류 상태 |
| AMR | `/amr_01/get_task` | 사용자 정의 Service | 명령 ID로 결과·진행 조회 |
| 협동로봇 | `/arm_01/execute_program` | 사용자 정의 Action | 사전 정의 작업 실행 |
| 협동로봇 | `/arm_01/state` | 사용자 정의 Topic | 준비·실행·오류 상태 |
| 공통 | `/<device>/set_paused` | 사용자 정의 Service | 중단이 아닌 일시정지 정책 |
| 공통 | `/<device>/reset_fault` | 사용자 정의 Service | 조건부 오류 해제 |

Action의 취소를 일시정지·재개와 동일시하지 않는다. 일시정지 지원 여부와 재개 정책은 장비 계약에서 별도로 정한다.

### 최소 필드 제안

- Goal: `command_id`, `device_id`, `target/program_id`, 필요한 작업 파라미터.
- Feedback: `phase`, `progress`, `current_pose/current_step`, `error_code`.
- Result: `outcome`, `error_code`, `message`, `final_state`.
- State: `boot_id`, `sequence`, `device_mode`, `task_state`, `active_command_id`, `stamp`.
- 테스트 로그 전용: `run_id`, `scenario_id`, `sim_epoch`, `backend_mode`.

실제 장비 계약에 없는 테스트 필드를 임의로 외부 인터페이스에 추가하지 않는다. 이 경우 테스트 실행기에서 별도의 상관관계 테이블을 관리한다.

## 2.6 작업 수명주기와 중복 방지

### 업무 상태 모델 제안

정상 경로:  
`IDLE → ACCEPTED → EXECUTING → SUCCEEDED → IDLE`

예외 경로:

- 접수 전 거부: 작업을 시작하지 않고 거부 이유 반환.
- 실행 실패: `EXECUTING → FAILED`.
- 취소 처리: `EXECUTING → CANCELING → CANCELED`.
- 장비 오류: 작업 결과와 장비의 `FAULTED` 운전 상태를 별도로 기록.
- 재시작 후 불명확한 작업: `UNKNOWN`으로 조회되도록 정책 정의.

업무 상태와 ROS 2 Action 프로토콜 상태는 별도 매핑 표로 관리한다.

### 명령 원장 정책

- `command_id`를 업무 식별자로 사용하고 ROS Action Goal UUID와 연결한다.
- 같은 ID·같은 내용의 재요청은 재실행하지 않고 기존 상태·결과를 반환하도록 설계한다.
- 같은 ID·다른 내용은 오류로 처리한다.
- 재시작 복구 시험에는 원장을 로컬 파일 또는 데이터베이스에 보존한다.
- Action 결과 캐시에만 의존하지 않고 조회 Service 또는 상태 스냅샷을 제공한다.
- 취소 요청 응답과 실제 동작 중단 확인을 구분한다.
- 완료와 취소가 경합할 때의 최종 상태 규칙을 명시한다.

이 정책은 프로젝트에서 구현하는 기능이다. ROS 2 미들웨어가 업무 단위의 정확히 한 번 실행을 대신 보장한다고 가정하지 않는다.

## 2.7 실행 Backend

### Backend 공통 내부 계약

다음은 프로젝트 내부 메서드 개념이며 ROS 표준 API가 아니다.

- `start`: 목표와 실행 파라미터 전달.
- `cancel`: 중단 요청.
- `pause/resume`: 해당 장비에서 지원할 때만 사용.
- `observe`: 실제 위치·관절·진행 상태 수집.
- `health`: 실행 가능·통신 상태.
- `reset`: 초기화 절차에서만 수행.

### AMR — 최소 실행 방식

- 사전에 정의한 경유점 목록을 사용한다.
- 단순 경로 추종과 속도 제한으로 이동시킨다.
- 차륜 구동은 선택한 Isaac 로봇 예제의 컨트롤러를 활용한다.
- 가상 제어기는 Isaac 위치 피드백을 바탕으로 도착을 판정한다.
- 지정 경로 방식에는 자율 장애물 회피가 없음을 명시한다.
- 이동 장애물에 대한 경로 재계획 시험이 필요할 때만 Nav2를 추가한다.

NVIDIA는 ROS 2 Bridge와 Nav2를 연결하는 내비게이션 예제를 제공한다. 본 프로젝트에서는 선택적 확장으로만 사용한다. [S05]

### 협동로봇 — 최소 실행 방식

- `HOME → APPROACH → WORK → RETRACT → HOME` 같은 관절 자세 순서를 정의한다.
- 관절 명령과 관절 상태 피드백을 연결한다.
- 허용 오차 안에서 일정 시간 유지되었을 때 해당 단계를 완료한다.
- 화물 인계는 처음에는 논리적 부착·분리 모델로 처리하고 로그에 단순화 모델임을 표시한다.
- 초기에는 역기구학·충돌 회피 계획·힘 제어를 개발하지 않는다.

Isaac Sim 공식 관절 제어 예제는 ROS 2 메시지를 통한 관절 명령·상태 연결의 출발점으로 사용할 수 있다. [S04]

## 2.8 QoS·연결 상태·시간

### QoS 초기 정책안

| 데이터 | 제안 정책 | 확인할 사항 |
|---|---|---|
| 장비 상태 스냅샷 | Reliable, Volatile, 제한된 큐 | 늦은 구독자는 다음 주기 또는 조회로 복구 |
| 작업 이벤트 | Reliable, Volatile | 누락 복구는 명령 원장 조회로 보완 |
| 위치·관절 피드백 | 실제 발행자와 호환되는 설정 | Best Effort/ Reliable 조합 사전 점검 |
| `/clock` | Bridge 기본 설정에서 시작 | 모든 참여 노드와 호환성 확인 |
| Action/Service | 라이브러리 기본값에서 시작 | 개별 변경은 필요성과 영향을 시험 |

DDS 기반 ROS 2에서는 QoS가 호환되지 않으면 데이터가 전달되지 않을 수 있다. 설정 파일과 실행 로그에 실제 QoS를 남긴다. [S10][S12]

### 연결 상태 제안

- DDS Discovery 여부와 장비 업무 준비 상태를 구분한다.
- 주기적 State 수신, `boot_id`, 마지막 수신 시각으로 장비 건강 상태를 판단한다.
- 프로세스가 살아 있어도 이동 Backend나 Isaac Sim이 멈추면 `NOT_READY`로 보고한다.
- 정상 시험에서 오래된 명령이 반복 적용되지 않도록 제어 명령 watchdog을 둔다.

### 시간 정책 제안

- 물리 진행·위치 데이터: 시뮬레이션 시간.
- Adapter 통신 지연·실제 타임아웃: 단조 증가하는 실제 시간.
- 로그 상관관계: 실제 UTC 시각과 시뮬레이션 시간을 함께 기록.
- 다중 호스트의 편도 지연은 시계 동기화가 검증된 경우에만 해석한다.
- Isaac 모드에서는 `/clock` 발행자를 하나로 정한다.
- 경량 모드에서는 자체 시험 시계를 사용하며 Isaac 시계와 동시에 발행하지 않는다.

Isaac Sim은 `/clock`을 통해 ROS 2 노드에 시뮬레이션 시간을 제공할 수 있다. 물리 실행을 멈추면 시뮬레이션 시간 기반 처리도 멈출 수 있으므로 감시 타이머와 분리한다. [S06]

## 2.9 라이브러리·도구 선택

ROS 2 Jazzy에는 `rclpy`, `launch_ros`, 메시지·TF 패키지, `launch_testing`, `rosbag2` 등 관련 패키지가 제공된다. 아래는 이 프로젝트에서의 사용 제안이다. [S11]

| 분류 | 라이브러리·도구 | 사용할 목적 |
|---|---|---|
| 필수 | `rclpy` | Python 가상 제어기·Action/Service/Topic 구현 |
| 필수 | `launch`, `launch_ros` | 장비별 실행 및 파라미터·Namespace 적용 |
| 필수 | `colcon`, `ament`, `rosdep` | 빌드·의존성 관리 |
| 필수 | ROS 2 CLI | 노드·Topic·Service·Action 연결 확인 |
| 필수 | 표준 메시지 패키지 | 위치·속도·관절·시간 데이터 교환 |
| 권장 | `tf2_ros` | 좌표계 변환 및 확인 |
| 권장 | `rosbag2` | 선택한 Topic의 기록·사후 분석 |
| 권장 | `launch_testing` + Python 테스트 | 프로세스 포함 자동 회귀 시험 |
| 선택 | RViz2 | 위치·TF·센서의 기술적 디버깅 |
| 선택 | Nav2 | 자율 이동·장애물 회피와 관련된 시험 |
| 선택 | MoveIt 2 / `ros2_control` | 실제 모션 스택 인터페이스가 필요할 때 |
| 선택 | `rclcpp` | 측정으로 확인된 Python 병목 부분 대체 |

빌드 도구 설치 절차는 NVIDIA의 ROS 워크스페이스 구성 안내도 참고한다. [S01] `ros2_control`은 초기 필수가 아니며, Isaac 내 통합 방식과 제공 여부는 선택한 릴리스에서 확인한다. 현재 문서에는 인프로세스 Controller Manager 방식도 설명되어 있다. [S09]

# 3. Isaac Sim 구성과 사용 기술

## 3.1 역할

Isaac Sim 계층에는 다음 책임만 둔다.

1. 가상 공간과 로봇·설비 에셋 로딩.
2. 이동·관절 동작 실행.
3. 위치·관절·점유·접촉 등 관측 데이터 생성.
4. 시뮬레이션 실행·정지·초기화.
5. 개발자용 화면 표시.

로봇·씬을 Python으로 구성하는 Core API와 여러 로봇 예제를 공식 입문 자료에서 확인할 수 있다. [S08]

**업무 명령의 접수·중복 방지·오류 코드·재시도 정책은 외부 ROS 2 가상 제어기에 남긴다.**

## 3.2 기술 구성과 책임

| 기술·도구 | 역할 | 적용 범위 |
|---|---|---|
| OpenUSD / USD 에셋 | 씬·로봇·설비 구성 | 전체 모델 관리 |
| PhysX 기반 물리 | 강체·관절·충돌 동작 | 필요한 장비에 한정 |
| Isaac Sim Python / Core API | 장비 배치·상태 읽기·시뮬레이션 제어 | 자동 환경 구성 |
| ROS 2 Bridge | ROS 2 메시지와 시뮬레이터 연결 | 표준 명령·상태 연결 |
| OmniGraph / Action Graph | 데이터 흐름과 제어 노드 연결 | Bridge·제어 연결에 한정 |
| URDF Importer | 보유 로봇 모델 가져오기 | 기존 USD가 없을 때 |
| Standalone 실행 | 스크립트 기반 실행 관리 | 반복 시험·자동화 |

Core API·OmniGraph·센서·임포터 관련 튜토리얼은 공식 색인에 정리되어 있다. [S08][S14] URDF Importer의 관절·물리 설정은 가져온 뒤 검토한다. [S07] Standalone에서는 물리·렌더링 스텝을 제어할 수 있지만 실제 시간과 동일한 속도로 진행된다고 보장되지는 않는다. [S03]

## 3.3 ROS 2 Bridge 인터페이스

외부 업무 Action을 Bridge가 자동으로 물리 동작으로 바꿔준다고 가정하지 않는다. 그 변환은 ROS 2 실행 Backend에서 구현한다.

### AMR 하부 연결안

| 방향 | 이름 예시 | 메시지 후보 | 처리 |
|---|---|---|---|
| ROS → Isaac | `/sim/amr_01/cmd_vel` | `geometry_msgs/Twist` | 선택한 차륜 컨트롤러로 전달 |
| Isaac → ROS | `/sim/amr_01/odom` | `nav_msgs/Odometry` | 위치·속도 피드백 |
| Isaac → ROS | `/tf` | `tf2_msgs/TFMessage` | 장비별 변환 |
| Isaac → ROS | `/sim/amr_01/scan` | `sensor_msgs/LaserScan` | Nav2가 필요할 때만 |

`Twist`/`TwistStamped` 선택은 사용한 Bridge 노드와 내비게이션 버전에 맞춰 고정한다. 필요 시 외부 Backend에서 변환한다.

초기에는 위치를 직접 변경하는 텔레포트 방식보다 차륜 구동과 위치 피드백을 우선한다. 위치를 직접 변경하는 단순화 모드를 쓰면 충돌·주행 물리 시험으로 판정하지 않는다.

### 협동로봇 하부 연결안

| 방향 | 이름 예시 | 메시지 후보 | 처리 |
|---|---|---|---|
| ROS → Isaac | `/sim/arm_01/joint_command` | `sensor_msgs/JointState` | 관절 목표값을 Articulation 제어로 연결 |
| Isaac → ROS | `/sim/arm_01/joint_states` | `sensor_msgs/JointState` | 실제 관절 피드백 |
| Isaac → ROS | `/tf` | `tf2_msgs/TFMessage` | 필요 시 로봇 링크 변환 |

`JointState`를 관절 명령으로 사용하는 것은 Isaac의 해당 예제 패턴을 따르는 하부 연결이다. 모든 로봇 제어기의 공통 표준 명령 인터페이스로 일반화하지 않는다. [S04]

실제 Adapter가 `FollowJointTrajectory` 같은 특정 인터페이스를 요구하면 별도 프로파일로 구현한다. 복잡한 궤적 제어기 자체를 개발하기보다는 호환되는 기존 제어 스택을 검토한다. [S09]

## 3.4 모델·씬 구성안

### AMR

- 초기에는 예제에서 동작 확인이 쉬운 차동 구동 로봇 한 종류를 선택한다.
- 동일 모델을 10개의 독립 인스턴스로 배치한다.
- 장비별 Prim 경로·Namespace·초기 위치·속도·보고 주기를 설정한다.
- 실제 벤더 외형과 주행 특성 재현은 Adapter 계약 검증 이후로 미룬다.

### 협동로봇

- 관절 명령 예제와 맞는 로봇 한 종류로 시작한다.
- 동일 모델 5개를 서로 다른 작업 셀에 배치한다.
- 모델별 관절 이름·순서·제한을 설정 파일에 저장한다.
- 그리퍼 없이 관절 작업부터 검증한 후 논리 인계를 추가한다.

### 물류 설비

- Conveyor: 구간별 점유와 이송 완료.
- Lift: 층·도어·점유·이동 시간.
- AS/RS: 입출고 포트·저장 위치·재고 상태·처리 시간.
- 물리 이동이 필요 없는 내부 동작은 ROS 2 상태 모델로 구현한다.
- Isaac에는 위치·점유·이송 등 테스트에 필요한 표현만 둔다.

**PLC 경계:** 현재 가정에서는 설비 제어기도 ROS 2 인터페이스를 제공한다. 이후 실제 PLC Adapter가 Modbus·OPC UA·벤더 프로토콜을 사용하면, 그 프로토콜 서버를 별도 추가해야 한다. ROS 2 설비 모델만으로 실제 PLC 통신을 검증했다고 판단하지 않는다.

### 씬 경로 제안

- `/World/Environment`: 바닥·벽·작업대.
- `/World/AMRs/amr_01` ~ `/World/AMRs/amr_10`.
- `/World/Arms/arm_01` ~ `/World/Arms/arm_05`.
- `/World/Equipment`: Conveyor·Lift·입출고 포트.
- `/World/Cargo`: 화물.
- `/World/TestMarkers`: 도착·인계 영역.

씬 원본과 장비별 설정을 분리한다. 동일 장비를 복제할 때는 ROS 이름·물리 객체 경로·초기 위치가 모두 독립적인지 검사한다.

## 3.5 센서·물리 상세도

| 항목 | 초기 정책 | 추가 조건 |
|---|---|---|
| 위치·관절 피드백 | 필수 | 완료 판정에 사용 |
| 구역 점유 | 논리 영역 판정 | 상세 센서 재현이 필요하면 확대 |
| 충돌 관측 | 중요한 이동 구간 위주 | 충돌 판정 기준·지속 시간 정의 |
| LiDAR | 기본 제외 | Nav2·장애물 관련 시험 |
| 카메라 | 기본 제외 | 인식 관련 Adapter 계약이 있을 때 |
| 정밀 파지 | 기본 제외 | 실제 파지 성공이 업무 결과에 필요할 때 |

센서 구현 선택지는 공식 센서 튜토리얼을 참고하되, 이번 환경에서는 Adapter 결과에 필요한 데이터만 생성한다. [S14]

## 3.6 Python·버전 호환성과 재현성

NVIDIA의 ROS 설치 문서는 표준 메시지와 사용자 정의 인터페이스 사용 시 런타임 준비 방법을 구분한다. Python·ROS 라이브러리 요구 사항은 Isaac Sim 릴리스에 따라 달라질 수 있다. [S01]

따라서 다음 정책을 제안한다.

- 사용자 정의 Action/메시지는 외부 ROS 2 워크스페이스에서만 우선 사용한다.
- Bridge 내부는 표준 메시지 위주로 구성한다.
- Isaac 내부 Python 환경과 외부 ROS 워크스페이스 환경을 무조건 혼합하지 않는다.
- 사용자 정의 패키지를 Isaac 안에서 직접 불러와야 할 때만 해당 릴리스의 빌드 절차를 따른다.
- 확정한 Isaac 버전·ROS 배포판·RMW·Python·드라이버·에셋·예제 커밋을 실행 보고서에 기록한다.
- 과거 버전 예제 코드를 현재 버전에 그대로 적용하지 않는다.

## 3.7 실행·초기화 순서

### 시작

1. 시험 실행 ID와 설정 해시 생성.
2. Isaac 프로세스 시작 및 씬 로딩.
3. Bridge·물리 객체·필수 Topic 준비 확인.
4. 시뮬레이션 시작 및 `/clock` 진행 확인.
5. 가상 제어기의 위치·관절 피드백 수신 확인.
6. 장비를 `READY`로 전환.
7. 기록기·판정기 준비 완료 후 Adapter 시험 명령 시작.

단순 대기 시간보다 실제 준비 조건을 확인한다. 다만 준비되지 않는 경우를 위한 실제 시간 기준 타임아웃을 둔다.

### 초기화

1. 새 시험 명령 차단.
2. 진행 중 작업 중단·종료 처리.
3. Backend 정지·씬 상태 복원.
4. 원장·화물·점유·장애 상태를 초기화 정책에 맞춰 처리.
5. `sim_epoch` 증가, 지연 도착한 이전 실행 메시지 무효화.
6. 피드백 안정화 확인 후 재개.

재시작 복구 시험에서는 원장·화물 상태를 의도적으로 유지하는 프로파일을 사용한다. 깨끗한 초기화 시험과 섞지 않는다.

## 3.8 하드웨어·성능 접근법

확정 GPU 모델이나 실시간 처리 가능 대수는 현재 정보로 확인할 수 없다. 공식 요구 사항과 Compatibility Checker를 먼저 확인하고 실제 장면으로 측정한다. [S13]

측정 순서:

1. AMR 1대 + 협동로봇 1대.
2. AMR 3대 + 협동로봇 2대.
3. AMR 10대 + 협동로봇 5대.
4. 필요한 센서를 단계적으로 추가.
5. 화면 표시 유무와 기록 활성화 유무를 나눠 비교.

측정값:

- CPU·GPU·메모리·VRAM.
- 물리 스텝 처리 시간.
- 실제 시간 대비 시뮬레이션 진행률(RTF).
- ROS 상태 발행·수신 빈도.
- 명령 응답 지연과 Backend 실행 지연.
- 로그·기록기의 부하.

GUI를 끄는 시험도 센서·물리 비용까지 사라진다고 가정하지 않는다. 병목이 확인되기 전에는 GPU 추가 구매나 분산 구성을 전제하지 않는다.

# 4. 테스트·관측 설계

## 4.1 정상 시험

1. Adapter가 AMR 이동 작업을 제출한다.
2. 가상 제어기가 목표·운전 상태·사용 중 여부를 검증한다.
3. Isaac Backend가 이동을 시작한다.
4. 실제 위치가 도착 조건을 만족하면 이동 완료를 반환한다.
5. 협동로봇 셀의 인계 조건을 확인한다.
6. 협동로봇 작업이 실행되고 관절 상태로 완료를 확인한다.
7. 논리 화물 소유권을 이전한다.
8. 검증기가 명령·작업·화물 상태의 일치를 판정한다.

단순화한 화물 인계는 물리 파지 시험과 별도 결과 항목으로 표시한다.

## 4.2 장애 시험 매트릭스

| 상황 | 주입 계층 | 확인할 Adapter 동작 |
|---|---|---|
| 장비 사용 중 | 가상 제어기 | 거부 결과를 실패·대기로 정확히 변환 |
| 명령 접수 지연 | 가상 제어기 | 타임아웃 및 재요청 처리 |
| 이동 중 정지 | Backend | 진행 정체와 실행 실패 구분 |
| 완료와 취소 경합 | 가상 제어기 | 최종 결과 중복 처리 방지 |
| 상태 보고 누락 | 상태 발행 모듈 | 오래된 상태 탐지 |
| 제어기 프로세스 종료 | 실행 관리 계층 | 연결 상실·작업 불명확성 처리 |
| 제어기 재시작 | 가상 제어기 | `boot_id` 변경과 상태 복구 |
| 잘못된 장비 ID·프레임 | 인터페이스 경계 | 오배달·좌표 오류 차단 |
| 지연·손실 | 별도 네트워크 시험 환경 | 통신 복구와 타임아웃 |
| Isaac만 일시정지 | 시뮬레이션 계층 | 시뮬레이터 정지와 장비 오류 구분 |

**중복 시험은 두 종류로 구분한다.**

- 업무 중복: 같은 `command_id`를 가진 새 Goal을 다시 제출.
- 전송 계층 문제: 지연·손실·재전송 조건을 별도로 부여.

단순 노드 종료는 네트워크 단절과 같지 않다. 두 시나리오를 분리한다. 오류 문자열·중복 완료 등도 유효한 ROS 프로토콜 범위 안에서 업무 메시지로 주입한다.

## 4.3 로그 스키마

### 공통 상관관계

- `run_id`, `scenario_id`, `device_id`.
- `command_id`, Action Goal UUID.
- `boot_id`, `sequence`, `sim_epoch`.
- `backend_mode`, 설정 해시, 인터페이스 버전.

### 시각과 상태

- 실제 UTC 시각.
- 프로세스 단조 시간과 측정 구간.
- 시뮬레이션 시간.
- 이전·이후 상태.
- 오류 코드·주입 장애 ID.
- 요청·응답 요약 및 필요한 원문.
- 현재 위치·관절·화물·점유 상태.

### 저장 제안

- 이벤트: JSON Lines.
- 정량 지표: CSV.
- 선택한 ROS Topic: rosbag2.
- 최종 결과: Markdown 또는 JUnit 형식.
- 영상: 실패 케이스 분석이 필요할 때만 선택.

rosbag2는 ROS 2 기록 도구로 사용하되, 본 설계에서는 모든 Action 요청·응답·업무 의미가 자동으로 완전 기록된다고 전제하지 않는다. 명령 원장과 이벤트 로그를 함께 남긴다. [S11]

## 4.4 지표와 측정 구간

| 지표 | 정의 |
|---|---|
| 명령 접수 지연 | Adapter 상위 요청부터 장비 접수 결과까지 |
| Adapter 내부 지연 | Adapter 수신부터 장비 인터페이스 송신까지 |
| 장비 결과 전달 지연 | 제어기 결과 생성부터 Adapter 상위 통지까지 |
| 작업 시간 | 접수부터 성공·실패·취소 확정까지 |
| 상태 신선도 | 마지막 상태 수신 이후 실제 경과 시간 |
| 중복 실행 수 | 같은 업무 명령의 실제 실행 횟수 초과 |
| 상태 불일치 수 | 기대·실제·보고 상태가 계약을 위반한 횟수 |
| 복구 시간 | 장애 해제부터 정상 상태 재확인까지 |
| RTF | 경과 시뮬레이션 시간 ÷ 경과 실제 시간 |

Adapter 내부 지연은 Adapter 측 계측이 제공되어야 측정할 수 있다. 외부 관측만 가능하면 왕복·종단 지연으로 보고하고 내부 지연으로 오표기하지 않는다.

## 4.5 부하 프로파일 초안

아래 수치는 제품 성능 요구 사항이 아니라 **측정 시작을 위한 제안값**이다.

- 장비 상태: 장비당 1 Hz → 5 Hz → 10 Hz.
- 15대가 각각 상태 Topic 하나를 10 Hz로 발행하면 상태 메시지만 초당 150개.
- TF·관절·위치·Action 통신·센서는 별도 부하로 계산.
- 명령 부하: 순차 → 동시 → 순간 집중.
- 정상 완료·거부·취소·오류 비율을 설정에 기록.
- 명령 접수 지연 p50/p95/p99와 CPU·메모리·큐 길이를 수집.
- 워밍업과 측정 구간을 분리하고 반복 횟수를 기록.
- 메모리 증가와 원장·큐 크기에 상한 또는 정리 정책을 둔다.

15대 구성은 초기 목표 부하이며, 시스템 최대 처리량 시험과 동일하지 않다. 최대치는 경량 모드에서 장비 수·빈도·작업률을 독립적으로 늘려 측정한다.

## 4.6 초기 합격 기준 제안

정확한 지연 수치는 Adapter 요구 사항 확정 후 결정한다. 먼저 다음 정합성 기준을 적용한다.

- 명령이 다른 장비에 적용되는 사례 0건.
- 같은 업무 명령의 중복 실행 0건.
- 정의된 조건을 충족하지 않은 성공 보고 0건.
- 취소·실패·완료 결과의 모순 0건.
- 시험 종료 시 미확정 작업은 0건 또는 명시적인 `UNKNOWN` 정책으로 설명.
- 상태·원장·화물 소유권 불일치 0건.
- 부하 시험에서 큐·메모리의 무제한 증가 없음.
- 실시간 시험은 합의한 RTF와 상태 보고 주기를 충족한 실행만 유효 표본으로 인정.

# 5. 전체 개발 로드맵

## 5.1 기간 가정

아래 기간은 **Python 개발 경험이 있고 ROS 2·Isaac Sim은 입문 수준인 개발자 1명**이 예제 에셋을 재사용한다는 조건의 계획용 추정치다.

- 통합 관리 시스템·Adapter 개발 기간은 제외.
- 맞춤 CAD 제작·실제 벤더 제어기 재현·복잡한 PLC 프로토콜 구현은 제외.
- 설치 이슈·장비 계약 변경·센서·Nav2 확장에 따라 달라진다.
- 전체 초기 범위는 약 **8~12주 수준의 계획안**으로 보고 1단계 완료 후 재산정한다.
- 기간보다 단계별 종료 조건을 우선한다.

## 5.2 단계별 계획

| 단계 | 계획용 기간 | 구현 내용 | 종료 조건 |
|---|---|---|---|
| 0. 환경·계약 확정 | 0.5~1주 | 버전·장비 계약·시간 정책·로그 정의 | 호환성 확인, 계약 v0.1 승인 |
| 1. 경량 AMR | 1~1.5주 | Action·State·원장·취소·오류 | 실제 Adapter 또는 상위 시험 경로로 정상·오류 검증 |
| 2. Isaac AMR 1대 | 1~1.5주 | 씬·Bridge·이동·피드백 | 실제 위치 기반 완료 판정 |
| 3. 협동로봇 1대 | 1~1.5주 | 관절 시퀀스·작업 Action·인계 | AMR→협동로봇 인계 상태 일치 |
| 4. 다중 장비 | 1~1.5주 | 설정 기반 10대+5대 생성 | Namespace·TF·작업 격리 확인 |

| 6. 운영화·보완 | 0.5~1주 | 실행 패키징·버전 고정·문서화 | 다른 개발자가 재현 가능 |

### 0단계 — 환경과 인터페이스를 먼저 고정

산출물:

- OS·GPU 드라이버·Isaac·ROS·RMW 조합.

- 상태·오류·취소·재시작 정책.
- 단위·좌표계·시간·QoS 규칙.
- 장비 수·주기·필수 로그와 판정 기준.

- 선택한 Isaac 릴리스에서 공식 예제가 실행되는가?
- Adapter가 실제로 사용할 인터페이스가 정해졌는가?
- AMR 목적지/경유점/경로 중 어디까지 제어하는가?
- 협동로봇은 작업 프로그램 호출인가, 관절 궤적 명령인가?

### 1단계 — Isaac 없이 ROS 2 가상 AMR부터

구현:

- 타이머 기반 이동 완료.
- 정상·거부·실패·취소.
- 명령 원장과 중복 방지.
- 상태 발행과 재시작 식별.
- 명령·결과 로그.

목적은 화면보다 먼저 **시험 장치의 장비 계약**을 검증하는 것이다.

### 2단계 — 가상 AMR 1대를 Isaac에 연결

구현:

- 표준 메시지 Bridge.
- 지정 경로 이동.
- 위치 피드백과 도착 조건.
- 시뮬레이션 시간과 실제 시간 분리.
- Backend가 멈췄을 때의 준비 상태·watchdog.

종료 조건은 화면에서 움직이는 것이 아니라 **Adapter 결과가 실제 가상 위치와 일치하는 것**이다.

### 3단계 — 협동로봇 및 인계

구현:

- 사전 정의 관절 작업.
- 관절 피드백 기반 단계 완료.
- AMR 도착·셀 점유·화물 존재 조건.
- 논리 화물 ID와 소유권 전이.
- 작업 중 취소·오류.

물리 파지는 추가 검증 목표가 생길 때만 개발한다.

### 4단계 — 목표 규모 10대+5대

구현:

- 장비 목록 설정 파일 기반 자동 생성.
- 독립 Namespace·프레임·Prim 경로.
- 장비별 속도·보고 주기·오류 프로파일.
- 동시 목표 실행.
- 장비별 프로세스 종료·재시작.
- CPU/GPU/RTF·상태 주기 측정.

10개의 서로 다른 벤더 제어기를 만드는 단계가 아니라, 우선 같은 프로파일을 여러 독립 장비로 확장하는 단계다. 벤더별 계약은 추가 프로파일로 개발한다.

### 5단계 — 자동 회귀와 성능 시험

- 동일 시나리오를 경량/Isaac Backend에서 각각 실행.
- 결과 의미가 같은지 비교.
- 성능 수치 비교에서는 Backend 차이를 명시.
- 장애별 합격·실패 결과 자동 생성.
- Adapter 내부 계측이 없으면 측정 가능한 범위만 보고.
- 장시간 시험의 로그 용량·원장 정리·메모리 증가 확인.

### 6단계 — 팀 단위 사용

- 실행 절차와 준비 상태 확인 자동화.
- 설정·에셋·버전 고정.
- CPU-only 경량 회귀와 GPU Isaac 회귀를 분리 운영.
- 신규 장비 프로파일 추가 가이드.
- 실패 재현 절차와 알려진 한계 문서화.

# 6. 구현 착수 전 미결정 사항

1. **AMR 계약:** 목적지만 전달하는가, 경유점·경로를 전달하는가?
2. **협동로봇 계약:** 작업 프로그램 호출인가, 관절 궤적 명령인가?
3. **인터페이스 출처:** 자체 정의인가, 실제 제어 시스템의 ROS 패키지가 있는가?
4. **장비 유형:** 동일 프로파일의 복수 장비인가, 여러 벤더의 서로 다른 계약인가?
5. **PLC 범위:** ROS 2 설비 모델까지만 필요한가, 실제 PLC 프로토콜 검증이 필요한가?
6. **실행 환경:** 보유 GPU·VRAM·CPU·RAM·OS는 무엇인가?
7. **요구 성능:** 명령률·상태 주기·지연 상한·복구 시간 요구가 있는가?
8. **실제 Adapter 준비 전:** 상위 테스트 클라이언트는 어느 팀이 제공하는가?

답이 없어도 0~1단계는 진행할 수 있지만, 실제 계약 없이 만든 인터페이스는 임시 프로파일로 표시해야 한다.

# 8. 최종 제안

**초기 기준 구성은 Ubuntu 24.04 + ROS 2 Jazzy + 지원되는 Isaac Sim 릴리스 + Python 가상 제어기로 한다. 정확한 릴리스·RMW·드라이버는 첫 단계에서 고정한다.**

구현 우선순위는 다음과 같다.

1. **필수:** 장비 인터페이스 계약과 상태·취소·오류·중복 정책.
2. **필수:** 경량 ROS 2 가상 AMR과 Adapter 연결 시험.
3. **필수:** Isaac AMR 1대·협동로봇 1대의 피드백 기반 실행.
4. **권장:** 설정 기반 10대+5대 확장, 자동 장애·복구·성능 시험.
5. **선택:** Nav2·MoveIt 2·상세 PLC·센서·정밀 물리.

**이 프로젝트의 핵심 산출물은 로봇 제어 알고리즘이 아니라, 실제 Adapter를 반복 가능하고 관측 가능한 조건에서 검증하는 가상 장비 시험 장치다.**
