# ROS 2 · Isaac Sim 스터디 가이드
## Adapter 검증용 가상 장비 환경 개발자 과정

- 작성 기준: 2026-09-21 KST
- 대상: AMR·협동로봇·PLC 설비 연동 경험이 있는 통합 시스템 개발자
- 목표: 외부 Adapter를 검증할 수 있는 ROS 2 가상 장비와 Isaac Sim 실행 환경 구성
- 목표 규모: AMR 10대 + 협동로봇 5대. 성능 보장 수치가 아니라 최종 실습 대상 수량이다.
- 형식: 개념 설명 + 설계 과제 + 실습 절차 + 합격 기준 + 복습 질문
- 검증 상태: 학습 설계 문서이며 실행 코드나 실제 시스템 실험 결과가 아니다.
- 저장 위치 제안: 저장소의 `docs/study/README.md`
- 예상 학습량: 기본 과정 30~45시간, 최종 프로젝트 10~20시간. 설치·GPU 문제 해결은 별도이며 숙련도에 따라 달라진다.

> 이 문서에서 인터페이스 이름, 수치, 상태 정책, 패키지 배치는 학습용 제안이다.
> 공식 기능 설명은 각 장의 참고문헌을 확인한다. 실제 장비의 인터페이스 계약이 있다면 그것이 우선이다.

## 1. 학습 목표와 범위

### 최종적으로 설명하고 구현할 수 있어야 할 것

1. Topic·Service·Action 중 어떤 인터페이스를 선택할지 설명한다.
2. 명령 접수와 물리 동작 완료를 구분한다.
3. 정상·취소·실패·통신 단절을 가상 장비에서 재현한다.
4. ROS 2 업무 상태 머신을 Isaac Sim 코드와 분리한다.
5. 경량 실행 모드와 Isaac 실행 모드에서 같은 외부 계약을 제공한다.
6. 명령 ID·작업 ID·장비 ID로 로그를 추적한다.
7. AMR 10대·협동로봇 5대로 확장하며 성능을 측정한다.

### 이번 과정에서 깊게 다루지 않을 것

SLAM 구현, 내비게이션 알고리즘 개발, 모터 제어기 설계, 힘 제어,
강화학습, 비전 피킹, 고정밀 파지, 안전 인증은 제외한다.
Nav2·MoveIt 2·센서 시뮬레이션은 필요해질 때 기존 예제를 실행하는 선택 과정으로 둔다.

### 역할 구분

- ROS 2: 노드 사이의 메시지·요청·작업 통신을 구성하는 기반.
- 가상 장비 제어기: 명령 수락, 상태 전이, 작업 종료, 장애 처리의 책임자.
- Isaac Sim: 가상 장면과 로봇 동작을 실행하고 관측값을 제공하는 시뮬레이터.
- ROS 2 Bridge: ROS 통신과 시뮬레이터 입출력을 연결하는 통로.
- 테스트 클라이언트: 실제 Adapter가 준비되기 전에 계약을 시험하는 대체 호출자.

ROS 2 인터페이스 개념은 [R1], Isaac Sim Bridge 실행 방식은 [I2]를 참고한다.
Bridge가 업무용 이동 Action이나 작업 완료 의미를 자동으로 만들어주는 것은 아니다.
업무 계약은 프로젝트에서 명시적으로 구현한다.

## 2. 환경 확정: 공부보다 먼저 할 일

### 2.1 버전 조합을 기록한다

`docs/environment.md`에 OS, ROS 배포판, Isaac Sim 버전, Python 환경,
RMW, 드라이버, GPU와 VRAM, 설치 방식, 공식 문서 버전을 기록한다.

ROS 학습 문서는 Jazzy 개념을 출발점으로 삼되, 실제 실행 환경은 선택한
Isaac Sim 릴리스의 공식 지원 표를 먼저 확인한다. 특정 버전 조합이 이미
검증되었다고 가정하지 않는다. NVIDIA 설치 안내 [I1]을 기준으로 결정한다.

이전 대화에서 참고한 Isaac Sim 5.1.0 문서는 조회 시 unsupported 안내가 있었다.
따라서 새 설치 기준으로 자동 채택하지 않는다. `latest` 문서도 변경되므로
설치 버전이 결정되면 같은 버전의 문서 URL을 환경 기록에 고정한다. [I0, I1]

### 2.2 환경을 분리한다

- 외부 ROS 노드: 선택한 ROS 배포판의 실행 환경.
- Isaac Sim: 해당 제품 버전에 맞는 실행 환경.
- 공통: 통신 계약과 설정 파일. 하나의 Python 가상환경을 강제로 공유하지 않는다.

특히 Isaac 프로세스 안에서 사용자 정의 ROS Python 패키지를 직접 import하는 구성은
별도 빌드·호환성 확인이 필요할 수 있다. 초기에는 사용자 정의 업무 인터페이스를
외부 ROS 노드에 두고, 시뮬레이터와는 지원되는 표준 인터페이스로 연결한다. [I1]

### 사전 완료 체크

- [ ] ROS 기본 예제의 발행·구독이 된다.
- [ ] Isaac Sim 기본 씬이 시작·정지된다.
- [ ] 선택한 버전의 Bridge 예제가 실행된다.
- [ ] 두 프로세스의 실행 명령과 환경변수 차이를 기록했다.
- [ ] 테스트 영역에 다른 개발자의 노드가 섞이지 않도록 설정했다.

## 4. 단계 1 — ROS 2 통신을 눈으로 확인하기

### 핵심 개념

- Node: 기능을 담당하는 ROS 소프트웨어 구성 단위.
- Topic: 지속적인 상태·이벤트 전달에 사용하는 발행·구독 인터페이스.
- Service: 짧게 끝나는 요청·응답.
- Action: 장시간 작업의 목표·피드백·결과·취소.
- Namespace: 여러 장비의 이름을 구분하기 위한 이름 공간.

장비가 여러 대라고 모든 메시지를 하나의 전역 이름으로 공유하지 않는다.
장비별 구분을 명시하는 것이 이번 실습의 설계 원칙이다. 인터페이스 선택은 [R1],
CLI와 패키지 학습 경로는 [R2]를 참고한다.

### 사용하는 도구

ROS CLI, rqt_graph, rqt_console, rclpy, colcon.
각 도구 설치와 명령 옵션은 선택한 ROS 배포판의 튜토리얼 [R2]을 따른다.

### 실습

1. 공식 turtlesim과 노드·Topic 이해 실습을 수행한다.
2. 노드 목록, Topic 타입, 발행자·구독자를 확인한다.
3. `amr_01` 가상 장비의 상태 발행기를 만든다.
4. 학습용 상태값을 IDLE → EXECUTING → IDLE로 변화시킨다.
5. 구독 노드를 실행하여 상태와 수신 시각을 기록한다.
6. 발행기를 종료하고 마지막 수신 이후 상태가 어떻게 보이는지 확인한다.

초기 탐색은 표준 메시지로 가능하지만, 프로젝트 단계에서는 장비 ID·작업 ID·
업무 상태·오류 코드를 갖는 명시적 메시지 계약으로 교체한다.

### 프로젝트 반영

`ros2_ws/src/testbed_devices/`와 `testbed_interfaces/`.
문서에는 Topic 이름, 타입, 주기, 좌표·단위, 소유자를 기록한다.

### 합격 기준

- [ ] 어떤 노드가 상태를 발행하는지 CLI로 설명한다.
- [ ] 발행기를 종료해도 마지막 상태를 무조건 정상 상태로 믿지 않는다.
- [ ] Topic 이름과 메시지 타입이 다른 문제를 구분한다.

### 질문

“상태가 EXECUTING이라는 메시지를 받았다”와 “장비가 지금 연결되어 있다”는 같은가?

**해설:** 아니다. 최근 수신 여부와 업무 상태는 별도로 판단하도록 설계해야 한다.
이 과제에서는 마지막 수신 시각 기반 통신 상태를 별도 필드로 기록한다.

## 5. 단계 2 — 이동 명령을 Action으로 모델링하기

### 핵심 개념

Action의 접수는 작업 성공이 아니다. 피드백은 진행 정보이고,
최종 결과는 성공·실패·취소 종료를 구별해야 한다. [R1, R3]

학습용 업무 상태는 IDLE, EXECUTING, STOPPING, FAULT로 시작한다.
업무 상태와 ROS Action 상태는 서로 다른 모델이므로 대응표를 작성한다.

### 이동 계약 설계 과제

프로젝트 예시인 `MoveTo` 계약에 다음을 정의한다.

- 요청: 업무 task_id, 목표 좌표, frame_id.
- 피드백: 현재 위치, 남은 거리, 업무 진행 상태.
- 결과: 결과 코드, 설명, 최종 위치.
- 정책: 이미 실행 중일 때 거부할지 큐에 넣을지.
- 중복 정책: 같은 task_id가 다시 오면 재실행할지 기존 결과를 반환할지.
- 취소 정책: 취소 접수와 실제 정지 확인을 구분.
- 성공 정책: 목표 위치·방향 오차와 유지 조건.

이 이름은 자체 실습 계약이며 기존 벤더나 Nav2 인터페이스와 같다고 가정하지 않는다.

### 실습

1. 공식 Python Action 서버·클라이언트 예제를 실행한다. [R3]
2. 계산 예제를 경량 가상 이동 작업으로 바꾼다.
3. 실행 중 주기적으로 진행 피드백을 반환한다.
4. 두 번째 목표가 들어왔을 때의 정책을 구현한다.
5. 취소, 실행 실패, 중복 요청을 각각 시험한다.
6. 업무 task_id와 ROS goal UUID의 연결을 로그에 남긴다.

### 합격 기준

- [ ] 명령 접수와 완료가 별도 이벤트다.
- [ ] 취소 요청 중에도 상태 보고가 유지된다.
- [ ] 최종 성공과 취소가 한 작업에 동시에 확정되지 않는다.
- [ ] 중복 task_id 정책을 테스트로 확인한다.
- [ ] 장비 재시작 후 결과 보존 여부를 문서화했다.

### 질문

이동 시간을 계산해 타이머가 끝나면 성공을 반환해도 되는가?

**해설:** 경량 모드의 명시적 모사 규칙으로는 가능하다.
Isaac 모드에서는 그 타이머만으로 실제 도착을 증명할 수 없다.
위치·속도 등의 관측값을 성공 판정에 사용한다.

## 6. 단계 3 — QoS와 콜백 문제를 직접 재현하기

### 핵심 개념

QoS는 reliability·durability·history 등을 통해 통신 동작을 설정한다.
DDS 기반 환경에서는 발행자·구독자의 QoS가 호환되지 않으면 데이터를
받지 못할 수 있다. [R4]

Executor는 콜백 실행을 담당한다. 콜백 그룹과 동기 호출을 잘못 조합하면
교착이나 다른 콜백의 지연이 생길 수 있다. MultiThreadedExecutor를 선택하는
것만으로 모든 차단 문제가 해결되지는 않는다. [R5]

### 실습 A: QoS

1. 이번 실습의 RMW를 고정한다.
2. 발행자·구독자 설정과 수신 여부를 표로 기록한다.
3. DDS 기반 실습에서 best-effort 발행과 reliable 구독 등
   공식 호환 표상 맞지 않는 조합을 재현한다.
4. 호환 설정으로 바꾼 뒤 수신이 재개되는지 확인한다.
5. 늦게 시작한 구독자에게 과거 상태를 전달할지 정책을 정한다.

### 실습 B: 콜백

1. 긴 작업과 상태 타이머를 함께 실행한다.
2. 작업 중 상태 보고·취소 처리가 지연되는 구현을 관찰한다.
3. 비동기 처리와 적절한 콜백 그룹 구성을 적용한다.
4. 동일 입력으로 수정 전후 응답 지연을 비교한다.

### 실습 C: 연결 단절

상태 발행기를 종료한 뒤 Adapter 대체 클라이언트가 일정 시간 내
UNKNOWN 또는 DISCONNECTED로 판단하게 한다.
임계 시간은 요구사항으로 정하고 물리 작업 성공 여부와 분리한다.

### 합격 기준

- [ ] QoS 불일치와 노드 미실행을 구분한다.
- [ ] 작업 중 취소 요청을 처리한다.
- [ ] reliable 설정만으로 업무 중복 방지까지 해결되었다고 판단하지 않는다.
- [ ] 재시도·작업 중복 방지는 별도 task_id 정책으로 시험한다.

### 질문

토픽이 목록에 보이는데 데이터는 안 들어오면 무엇을 볼 것인가?

**해설:** 실제 발행 여부, 타입, QoS, Namespace, 통신 설정,
시뮬레이션 정지 및 콜백 차단 여부를 차례로 확인한다.

## 7. 단계 4 — 설정으로 여러 장비를 띄우기

### 학습 내용

Workspace·Package·Launch·Parameter·Namespace를 공식 튜토리얼 [R2]에서 학습한다.

### 실습 설계

- 장비 ID: amr_01, amr_02, cobot_01.
- ROS 이름 예: `/amr_01/move_to`, `/amr_01/state`.
- fleet 설정: 장비 ID, 종류, 초기 위치, 속도 제한, 작업 시간.
- profile 설정: mock 또는 isaac Backend, GUI 여부.
- 업무 계약은 Backend에 관계없이 유지한다.

1. 단일 노드를 복사하지 말고 설정으로 여러 인스턴스를 실행한다.
2. AMR 3대와 협동로봇 경량 모델 2개를 실행한다.
3. 한 AMR만 종료하고 다른 장비의 처리에 영향을 주는지 확인한다.
4. 장비 ID 중복이나 설정 누락 시 시작 단계에서 실패하게 한다.
5. 가능하면 재시작 후 미완료 작업을 어떻게 보고할지 정의한다.

### 합격 기준

- [ ] 장비 대수 변경에 코드 수정이 필요 없다.
- [ ] 하나의 명령이 다른 장비로 전달되지 않는다.
- [ ] 장비 종류별로 파라미터 검증이 있다.
- [ ] 업무 상태 머신이 Isaac Sim 모듈을 import하지 않는다.

### 질문

Namespace만 나누면 좌표 프레임 이름 충돌도 자동으로 해결되는가?

**학습 과제의 정답:** 자동 해결을 가정하지 않는다.
TF를 도입할 때 frame_id·child_frame_id와 발행 주체도 별도로 설계하고 확인한다.

## 8. 단계 5 — Isaac Sim을 시뮬레이터로 이해하기

### 최소 개념

공식 기본 사용 튜토리얼 [I3]로 Stage의 객체를 선택·배치·저장하고
재생·정지 동작을 먼저 익힌다. 물리·로봇 세부 기능은 선택한 릴리스의
기본 로봇·Physics·Articulation 튜토리얼로 이어간다.

학습할 용어:
- USD / Stage / Prim: 장면 구성과 객체 참조를 이해하기 위한 개념.
- Transform: 위치·방향·크기.
- Rigid Body / Collision: 물체 움직임과 충돌 설정.
- Joint / Articulation: 연결된 로봇 관절 구조.
- Physics step / Render: 동작 계산과 화면·센서 표현의 구분.
- Timeline / Reset: 실행과 초기화.

### 실습

1. 바닥·작업대·상자만 있는 작은 씬을 만든다.
2. 상자를 물리 설정이 있는 경우와 없는 경우로 비교한다.
3. 제공 로봇 예제 하나를 불러와 초기 자세를 기록한다.
4. 씬 저장 후 다시 열었을 때 상태를 확인한다.
5. Standalone 예제로 실행·정지·초기화 흐름을 관찰한다. [I2]
6. GUI로 수행한 설정을 코드나 버전 관리되는 씬으로 재현한다.

### 주의점

화면에서 로봇 위치만 강제로 옮기는 실습과 바퀴·관절 동작을 통한
물리 검증은 별도 범위로 표시한다. 단순 이동 모사 결과를 실제 충돌·
동역학 검증이라고 보고하지 않는다.

### 합격 기준

- [ ] 씬을 다른 실행에서도 같은 설정으로 로딩한다.
- [ ] 초기 위치·좌표 단위·관절 초기값을 기록한다.
- [ ] 중지·재생·리셋이 각각 무엇을 초기화하는지 시험했다.
- [ ] 예쁘게 보이는 것과 물리 검증이 가능한 것을 구분한다.

### 질문

작업대 위에 상자가 보이면 적재 성공이라고 판단해도 되는가?

**해설:** 아니다. 이번 테스트의 적재 판정 조건을 먼저 정해야 한다.
위치 범위·점유 이벤트만 볼지, 접촉·안정 상태까지 볼지 검증 범위를 명시한다.

## 9. 단계 6 — ROS 2와 Isaac Sim 연결하기

### 연결 구조

Adapter 대체 클라이언트 → 업무 Action 서버 → Isaac 연결 Backend →
ROS 2 Bridge → 가상 로봇.

반대 방향은 로봇의 위치·관절 상태 → Bridge → Backend → 업무 피드백·결과다.

### 실습 순서

1. 선택한 버전의 공식 Bridge Standalone 예제를 실행한다. [I2]
2. 공식 이동 로봇 예제의 입력과 출력 Topic을 표로 정리한다.
3. 속도 입력을 전달하고 위치 또는 odometry 출력을 확인한다.
4. 단계 2의 업무 Action 서버에 이 Backend를 연결한다.
5. 직선 이동이나 지정 경로만 대상으로 도착 판정을 구현한다.
6. 취소 시 정지 명령을 보내고 관측값으로 정지를 확인한다.
7. 피드백이 사라졌을 때 성공하지 않고 오류 또는 미확정 상태로 처리한다.

명령 타입은 설치 버전의 예제와 계약에 맞춘다.
Twist·TwistStamped 등을 임의로 서로 같다고 취급하지 않는다.
Nav2는 이 단계의 필수 조건이 아니다.

### 시간 학습

ROS 2 Clock 공식 예제 [I4]로 `/clock`과 `use_sim_time`을 관찰한다.
5.1.0 예제는 개념 참고용이며 실행은 설치 버전의 동등 예제를 사용한다.

이 프로젝트의 설계 규칙:
- 작업·물리 시간: 시뮬레이션 시간.
- 통신 watchdog과 프로세스 생존 확인: 단조 증가 실제 시간.
- 로그: 두 시간과 run_id를 함께 기록.
- 공유 씬에서는 Clock 발행 주체를 하나로 지정.
- 경량 모드는 기본적으로 실제 시간을 사용하고, 별도 모의 Clock을 쓰면 문서화.

### 시간 장애 실습

시뮬레이션을 일시정지하고 ROS 노드는 계속 실행한다.
이어 리셋으로 시간이 되돌아오는 경우를 시험한다.
이전 작업 결과가 새로운 실행에 섞이지 않게 한다.

### 합격 기준

- [ ] 타이머가 아니라 관측된 도착 조건으로 Isaac 작업을 완료한다.
- [ ] 시뮬레이션 정지 시 통신 watchdog은 의도한 대로 동작한다.
- [ ] 피드백 중단과 작업 실패를 구별해 기록한다.
- [ ] 업무 task_id, 장비 ID, run_id로 전체 경로를 추적한다.

## 10. 단계 7 — 협동로봇과 설비 인계

### 실습 범위

정해진 관절 자세 순서를 실행하는 협동로봇 모델과
준비·점유·작업 완료 상태를 가진 설비 모델을 만든다.
정밀 파지·비전 인식·실제 PLC 스캔 주기 재현은 이번 과제에서 제외한다.

Isaac Sim ROS 튜토리얼 목록의 Joint Control·로봇 제어 예제를 학습 대상으로
사용한다. 해당 기능의 공식 목록은 [I5]에서 확인하고 설치 버전으로 이동한다.

### 업무 흐름

출고 버퍼 준비 → AMR 이동 → 도착·정지 확인 → 작업 셀 예약 →
협동로봇 작업 → 화물 상태 변경 → 예약 해제 → 완료 보고.

### 인터록 설계 과제

- 누가 셀 예약의 최종 소유자인가?
- AMR 도착 전 요청은 거부하는가, 대기시키는가?
- 작업 실패 때 화물 소유권은 어디에 남는가?
- 취소 시 로봇 정지와 셀 예약 해제를 어떤 순서로 하는가?
- 설비 재시작 후 실제 점유와 논리 점유를 어떻게 일치시키는가?

### 실습

1. 협동로봇 작업 프로그램 1개를 실행한다.
2. AMR이 없으면 시작을 거부한다.
3. 작업 중 실패를 주입하고 성공 이벤트가 발생하지 않는지 확인한다.
4. AMR 2대가 한 셀에 동시에 요청하도록 만든다.
5. 장애 중 재시작 시 화물 중복 처리 방지 정책을 시험한다.

### 합격 기준

- [ ] 단일 셀을 두 작업이 동시에 소유하지 않는다.
- [ ] 완료 이벤트가 화물 상태 변경과 모순되지 않는다.
- [ ] 실패 시 예약 해제와 상태 복구 정책이 있다.
- [ ] 물리 파지를 하지 않는 실습임을 결과에 명시한다.

## 11. 단계 8 — 재현 가능한 테스트와 성능 보고

### 테스트 계층 설계

- 단위: 상태 전이, 명령 중복 처리, 좌표·단위 변환.
- 계약: 외부 Action·Service·Topic의 의미.
- 통합: AMR 이동 후 협동로봇 인계.
- 장애: 연결 끊김, 취소 경합, 피드백 정지, 재시작.
- 성능: 동시 작업·상태량 증가·장시간 실행.

도구 학습은 pytest를 통한 로직 검사, ROS launch 기반 실행,
rosbag2를 통한 필요한 Topic 관찰·기록으로 구성한다.
ROS 기록·재생 입문은 [R2]의 관련 튜토리얼을 따른다.
Topic 재생만으로 전체 Action 대화와 외부 부작용이 동일하게 재현된다고
가정하지 않으며, 테스트 클라이언트가 명령을 다시 생성하도록 설계한다.

### 실험 매트릭스 제안

| 실험 | 대수 | Backend | 목적 |
|---|---|---|---|
| A | AMR 1 + 팔 1 | mock | 계약 확인 |
| B | AMR 3 + 팔 2 | mock | 경합·격리 |
| C | AMR 10 + 팔 5 | mock | Adapter 측 부하 |
| D | AMR 1 + 팔 1 | Isaac | 관측 기반 완료 |
| E | AMR 10 + 팔 5 | Isaac | 공정 정합성·실행 부하 |

대수·주기·실행 시간은 계획 값이다. 합격 수치는 요구사항과 실측 기준으로 확정한다.

### 필수 로그 설계

run_id, scenario_id, device_id, task_id, goal_uuid,
이벤트 종류, 이전/이후 상태, 실제 시각, 단조 증가 시각, 시뮬레이션 시간,
오류 코드, Git 커밋, 적용 설정, Backend 종류.

### 성능 해석

- 명령 접수 지연과 작업 완료 시간은 별도 지표다.
- p95/p99를 계산할 때 표본 수·측정 구간·워밍업 조건을 함께 기록한다.
- 서로 다른 컴퓨터의 단조 증가 시각을 직접 빼지 않는다.
- 초기에는 한 클라이언트의 요청/응답 왕복 시간을 사용한다.
- RTF는 측정 구간의 시뮬레이션 시간 증가량 / 실제 시간 증가량으로 정의한다.
- CPU, GPU, VRAM, 큐 길이와 상태 보고 간격도 기록한다.
- 무거운 로깅이 실험에 주는 영향도 비교한다.

### 합격 기준

- [ ] 같은 시나리오와 설정으로 다시 실행할 수 있다.
- [ ] 물리 결과의 완전한 비트 단위 결정성을 주장하지 않는다.
- [ ] mock/Isaac 결과를 검증 범위에 맞게 해석한다.
- [ ] 시뮬레이터 병목과 Adapter 병목을 분리해 설명한다.

## 12. 최종 프로젝트

### 과제

AMR 10대와 협동로봇 5대가 작업 셀을 공유한다.
외부 Adapter 또는 대체 클라이언트가 이동·작업·취소를 요청한다.
같은 인터페이스로 mock과 Isaac 모드를 선택한다.

### 필수 시나리오

1. 정상 운송·인계.
2. 이동 중 취소.
3. 동일 task_id 재전송.
4. 두 AMR의 같은 작업 셀 경합.
5. 협동로봇 실행 실패.
6. 상태 피드백 중단.
7. 가상 제어기 재시작.
8. Isaac 일시정지·리셋.
9. 동시 명령 부하.
10. 모든 작업 종료 후 점유·화물 정합성 검사.

### 제출물

- 환경 재현 문서.
- 외부 계약과 내부 Backend 인터페이스 명세.
- ROS 노드·Topic·Action 목록.
- 씬·장비 설정.
- 정상 및 장애 시나리오.
- 실행 보고서.
- 알려진 한계와 검증하지 않은 범위.

### 종료 조건

화면에서 로봇이 움직이는 것만으로 완료하지 않는다.
외부 계약, 실패 처리, 명령 추적, 재실행, 부하 측정까지 확인한다.

## 15. 최종 권장 순서

ROS 2 상태 통신 → Action과 상태 머신 → QoS·취소·재연결 →
설정 기반 다중 장비 → Isaac 기본 씬 → 관측 기반 동작 연결 →
협동로봇·설비 인계 → 10대+5대 자동 검증 순서로 진행한다.

첫 번째 목표는 “ROS 2로 AMR 한 대의 명령·상태·취소를 설명하고 시험할 수 있다”이다.
그 다음에 Isaac Sim을 붙여 시뮬레이션 결과와 업무 상태를 일치시키는 것이
Adapter 검증 목적에 맞는 학습 순서다.
